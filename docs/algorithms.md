# 算法与统计口径说明

本文列出项目中真正做过设计选择的算法，说明**怎么算、为什么这么算、边界情况怎么处理**。
不涉及具体实现的函数逐行解释 —— 那看代码更快，且代码有注释。

每个算法都对应一组单元测试，见文中标注的用例位置。

---

## 1. 榜单名次跨度（rank span）

**用途**：衡量一个条目在观察期内的名次波动，用于「哪些话题在快速上升」这类分析。

**定义**：对某数据集，按 `title` 分组，计算

```
出现次数 = count(快照数)
名次跨度 = max(rank) - min(rank)
```

**口径说明**：

- 用**全部快照**而不是最新快照 —— 跨度本身就是时间维度上的量，只看最新一帧恒为 0。
- `rank` 从 1 开始，**置顶条目用 0**（见 `utils/schema.py` 的约定）。
  这意味着置顶条目会天然产生「跨度 = 原名次」的大值。这是有意的：
  置顶确实意味着名次发生了剧烈变化。
- 排序时以「名次跨度」为主键、「出现次数」为次键降序。
  理由：只出现一次的条目跨度必为 0，如果不按出现次数做次级排序，
  一堆只上榜一次的长尾条目会和「真的没动过」的条目混在一起。

**边界**：豆瓣 Top250 这类长期榜在 20 个快照内名次零变化，跑出来是全 0 表。
这不是 bug，是榜单性质不同；单源分析里对这类榜单不出这张图。

> 实现：`analysis/common.py::rank_changes`；用例：`tests/test_analysis.py::TestRankChanges`

## 2. 榜单翻新速度（churn rate）

**用途**：回答「这个榜多久换一批」，用于比较实时榜与内容榜的差异。

**定义**：对某数据集的连续两天，取各自 Top N 的标题集合 `S(前) 、S(后)`，计算 Jaccard 系数

```
重合率 = |S(后) ∩ S(前)| / |S(后) ∪ S(前)|
```

取值 `[0, 1]`：1 = 两天完全一样，0 = 完全换了一批。

**为什么用 Jaccard 而不是「重叠数量 / N」**：后者在两天条目数不同的情况下会失真。
虽然本项目里 Top N 截断后集合大小通常相同，但采集失败导致某天只有 30 条时，
除法口径不同会得到大于 1 或明显偏低的值。Jaccard 对集合大小不敏感，更稳。

**每天只取最后一个快照**：同一天可能有多个快照（手动点了一次 + 定时任务跑了一次），
不筛的话「翻转率」会被同一批内部的重合冲高。
这一步由 `analysis/cross.py::latest_per_day` 统一处理。

**边界**：只有一天数据时算不出翻新率，返回**空表**而不是 0 ——
0 会被解读为「完全翻新」，与「无法计算」是两回事。

> 实现：`analysis/cross.py::churn_rate`；用例：`tests/test_analysis.py::TestChurnRate`

## 3. 最长公共子串判同话题（cross-source topic matching）

**用途**：判断两个不同榜单里的两条标题是不是在说同一件事。

**为什么不用分词 + 余弦相似度**：
1. 标题极短（10–30 字），分词后向量维度高但非零维很少，余弦相似度不稳定；
2. 需要维护一份领域词典，换话题领域就失效；
3. 更难解释 ——「最长公共子串 ≥ 5 个字」这个规则可以直接向人说明并验证。

**算法**：经典的动态规划最长公共子串（注意是**子串**不是子序列，
必须连续 —— 「同一话题」通常体现为连续短语，如「某某发布会」）。

```
L[i][j] = (a[i-1] == b[j-1]) ? L[i-1][j-1] + 1 : 0
best    = max L[i][j]
```

时间复杂度 `O(m·n)`，空间 `O(n)`（滚动数组）。

**阈值**：`min_lcs = 5`。经验值 —— 中文 4 字以下是常见词（「发布会」「开幕式」），
容易误判；5 字以上基本是具体短语。该参数暴露在函数签名上，可按语料调整。

**边界**：标题列里可能混入 NaN（长表合并后常见），实现中统一转成字符串再比较。
空串与任何串的 LCS 为 0。

> 实现：`analysis/cross.py::lcs_len`、`cross_topic`；用例：`tests/test_analysis.py::TestLcsLen`

## 4. Spearman 秩相关

**用途**：比较两个榜单的整体排序相似度（不看具体热度值，只看名次先后是否一致）。

**定义**：Spearman 相关系数等价于「对两列各自取秩，再算 Pearson」。

```
ρ = Pearson(rank(a), rank(b))
```

**为什么不用 Pearson**：热度值分布极度右偏（B 站播放量从几百到千万），
少数头部条目会完全主导相关性的计算结果。取秩后所有条目权重相同，
衡量的是「排序是否一致」，这才是榜单比较真正关心的。

**为什么不引入 scipy**：`scipy` 只为一个相关系数引入约 40 MB 依赖，
而取秩 + Pearson 一共两行（`pandas.Series.rank()` + `Series.corr()`）。
打包体积是桌面端的重要成本，这个取舍是明确做过的。

**性质与验证**：ρ 对严格单调变换不变 —— 用例里用
`[1,2,3,4]` vs `[1,10,100,1000]` 验证得 1.0。

> 实现：`analysis/common.py::spearman`；用例：`tests/test_analysis.py::TestSpearman`

## 5. 语料六项指标（corpus metrics）

文本分析页面上那六个指标卡，口径必须能讲清楚，逐个说明。

### 5.1 总文本条数 / 有效文本条数 / 缺失文本数量

```
总文本条数   = 表的总行数（含缺失）
有效文本条数 = missing == False 的行数
缺失文本数量 = 总 - 有效
```

**为什么「总」要包含缺失行**：如果只统计成功的，
那就没法知道到底漏了多少份文件 —— 而漏了多少恰恰是数据质量的核心信息。

### 5.2 总字数

两种口径都算，因为用途不同：

```
总字数               = Σ len(去空白后的文本)          # 含标点
总字数_只算汉字字母数字 = Σ 匹配 [一-鿿A-Za-z0-9] 的字符
```

前者用于和 Word 的「字符数」对照（用户熟悉的数字），
后者用于跨语料比较（不受标点习惯影响）。
两者并列展示而不是二选一，因为任何一个单独看都可能被误读。

### 5.3 总词数 / 去重词汇量 / 类型形符比（TTR）

```
总词数   = 分词后剔除纯标点词的 token 总数（tokens）
去重词汇量 = |{ normalize(t) | t ∈ tokens }|（types）
TTR      = types / tokens
```

**分词**：`jieba` 精确模式。剔除规则是「去掉空白后为空」或「整词全是标点」
（正则 `^[\W_]+$`，Unicode 模式，因此中文标点也会被识别）。

**归一化**：只做小写化（`str.lower()`）。中文不受影响，
英文让 `Python` / `python` 算同一个词。**不在分词前做小写化** ——
否则词频图里所有英文都会显示成小写，读起来别扭；小写化只在算去重时用。

**TTR 的已知局限**：TTR 随文本长度增加而系统性下降（长文本重复用词更多），
所以**不同长度的语料之间不能直接比 TTR**。项目里同时给出
「去停用词后的去重词汇量」，因为它比 TTR 更不受长度影响。
当 `tokens < 50` 时 TTR 无意义（1 个词也能算出 TTR = 1），
常量 `TTR_MIN_TOKENS` 记录了这个门槛。

### 5.4 平均句子长度

```
句子 = 按 [。！？；…!?;] 或换行切分，去空白后长度 ≥ 2 的片段
平均句子长度_字 = Σ 每句字数 / 句子数
平均句子长度_词 = Σ 每句词数 / 句子数
```

**为什么门槛是 2 个字**：「好。」「嗯！」这类片段不是句子，
计入会把平均值显著拉低。门槛值定义为常量 `MIN_SENT_CHARS = 2`。

**中文分句的困难**：中文没有空格分词，句号还可能出现在引号内、
小数点、省略号里。本项目选的是「只按句末标点和换行切」的保守方案 ——
覆盖率略低但误切少。更精细的做法需要句法分析，与本项目目标不匹配。

> 实现：`analysis/text.py`；用例：`tests/test_text_analysis.py`

## 6. 编码探测

**用途**：读取本地文档时确定编码。中文语料里 GBK 与 UTF-8 混杂是常态，
猜错就是整篇乱码。

**策略**：按 `utf-8-sig → utf-8 → gbk` 顺序尝试解码，**第一个不抛异常的胜出**。

**为什么是这个顺序**：
1. `utf-8-sig` 对「带 BOM」和「不带 BOM」的 UTF-8 都能正确解码且会去掉 BOM，
   所以放第一位；
2. GBK 放最后，因为它几乎能「成功」解码任何字节序列 ——
   如果把 GBK 放前面，UTF-8 文件会被错误解码成乱码而不报错。
   这是本算法最关键的一点：**顺序错了不会抛异常，只会静默产出乱码**。

**兜底**：三种都失败时用 `utf-8 + errors="replace"`，
保证不因一个文件中断批量处理，同时把编码标注成 `utf-8(replace)` 供排查。

**缺陷修复记录**：原实现把不带 BOM 的 UTF-8 也标注成 `utf-8-sig`，
因为 `utf-8-sig` 解码成功后没有区分是否真有 BOM。
解码结果本身正确，但每行 `note` 里的编码信息是错的，
排查乱码问题时会误导。现改为按字节前缀 `EF BB BF` 判断后如实标注。

> 实现：`extract/common.py::read_text_any`；用例：`tests/test_extract.py::TestReadTextAny`

## 7. robots.txt 判定与「带 `?` 规则」的特殊处理

**用途**：采集前确认站方是否允许抓取。这是项目的合规基础。

**基本判定**：用标准库 `RobotFileParser` 载入规则，用**我们实际在用的 UA** 去问
（不是 `*`）—— 因为有些站点对特定 UA 有单独规则。

**关键问题**：标准库在匹配前会丢弃 URL 的 query 部分。
实测某站点（zol）的 `/?*`、`/*html?*`、`/router.php?*` 三条规则**全部失效**，
带参数的 URL 一律被判为「允许」。

**对策**：

```
if robots 原文中存在带 ? 的 Disallow/Allow 规则
   and 目标 URL 带查询参数:
       → 拒绝（保守处理）
```

**为什么是「保守拒绝」而不是自己实现一个正确的 matcher**：
站方的规则写法千奇百怪（有的用正则、有的用通配符、有的写错），
自实现 matcher 会把「规则解析错误」和「站方意图」混在一起，
风险比直接拒绝更大。拒绝的代价只是少抓一些页面，
误判的代价是违反站方意愿，两者不对等。

**其他边界**：

| 情况 | 判定 | 理由 |
|---|---|---|
| `robots.txt` 返回 404 | 允许 | 站方明确表示没有规则（标准语义） |
| 网络错误 / 5xx | 允许，并记录原因 | 不能因为对方服务器抖动就整天不采集 |
| 同一域名第二次询问 | 走缓存，不发请求 | 采集几百个页面时这是性能关键 |

**缓存设计**：按**域名**（不是完整 URL）缓存，且 `None`（取不到）不写缓存 ——
否则一次网络抖动会让该域名在整个进程生命周期内都被当作「未声明」。

> 实现：`utils/net.py::is_allowed` / `get_robots`；用例：`tests/test_net.py::TestRobots`

## 8. 重试与限速（utils/http.py）

### 8.1 重试策略

| 情况 | 是否重试 | 理由 |
|---|---|---|
| 连接错误 / 超时 | 是（指数退避） | 典型的瞬时故障 |
| 429 Too Many Requests | 是，优先听 `Retry-After` | 站方明确说「慢点」，等就是了 |
| 500 / 502 / 503 / 504 | 是 | 服务端临时故障 |
| 403 / 404 | **否** | 站方明确拒绝，重试只会加重负担且更像攻击 |
| POST / PUT 等非幂等方法 | **否** | 重试可能造成重复提交 |

退避：`0.5s → 1s → 2s`（`BACKOFF_FACTOR = 0.5`，指数）。
服务端给了 `Retry-After`（秒数或 HTTP-date 两种格式都认）就听它的，
但上限 `RETRY_AFTER_CAP = 30` 秒，防止被恶意站点用超长头拖死整个采集进程。

### 8.2 一个真实的坑：重试不能交给 urllib3

第一版实现是给 adapter 设 `max_retries=Retry(...)`，让 urllib3 内部重试。
代码看起来完全正确，但**实测发现限速器只对第一次请求生效**：

```
min_interval = 5s，服务端一直返回 503
服务端实际被打了 3 次，间隔 [0.0, 1.0] 秒   ← 限速被绕过
```

原因是 `send()` 只被调用一次，urllib3 在 `super().send()` **内部**重发。
而 503 恰恰是最需要放慢的时候 —— 限速在最不该失效的地方失效了。

多个问题同源：`Retry-After` 的封顶也依赖 urllib3 2.x 的 `retry_after_max`
参数，光有个常量不传进去等于没有。

**改法**：adapter 关掉内部重试（`max_retries = 0`），重试写成
`RateLimitedAdapter.send()` 里的显式循环，**每次尝试前都过一遍限速器**。
代价是少了点 urllib3 的便利，换来「限速与重试在同一处、顺序确定」这个
可以讲清楚、也可以被测出来的保证：

```
同一场景改后：被打了 3 次，间隔 [1.0, 1.0] 秒（要求 ≥ 1.0）✓
```

这条经验值得记下来：**并发/重试这类逻辑，只读代码无法验证**。
必须让服务端数一下被打了几次包，才看得出真实行为。

### 8.3 限速

**按域名**的最小间隔限速（默认 1 秒），而不是全局限速。

**为什么按域名**：抓 A 站的等待不应该阻塞 B 站 ——
并发采集时全局限速会让五个站点排队，并发就失去意义。

**并发安全**：用一把锁保护「上次请求时间」的记录表，
但**锁内不睡眠** —— 先「预约」下一次可用时间点，出锁后再睡。
否则一个域的等待会阻塞所有其它域，等于退回全局限速。

**为什么用最小间隔而不是令牌桶**：榜单采集的速率要求本来就低
（一个站点每天几十次请求），间隔语义更直观，也更容易说明
——「保证对任一域名，相邻两次请求至少间隔 N 秒」。

**作用范围**：`GLOBAL_LIMITER` 是全进程共用的，所以同一进程里
所有会话对某域名的限速是一致的。但注意它的作用范围是**单进程** ——
`run_daily` 把五个站点跑在五个子进程里，每个进程各有一份记录。
这在实际使用中不构成问题（五个站点是五个不同域名），
但「跨进程也要限速」是个不同的问题，需要文件锁，当前不做。

> 实现：`utils/http.py`；用例：`tests/test_http.py`
> （其中 `test_retries_do_not_bypass_the_rate_limiter` 用本地
> `http.server` 打真实请求，就是为了守住上面这个坑）

## 9. 复杂度小结

| 算法 | 时间 | 空间 | 实际规模 |
|---|---|---|---|
| 名次跨度 | `O(n log n)` | `O(n)` | 2 万行 |
| 翻新率 | `O(d · n log n)` | `O(N)` 每源 | 天数 × Top N |
| LCS 判同话题 | `O(m·n)` 每对 | `O(n)` | m,n ≈ 10–30，对数 ≈ 900 |
| Spearman | `O(n log n)` | `O(n)` | 榜单规模 |
| 快照合并 | `O(F · R)` | `O(total)` | 164 文件 / 2 万行 |
| 编码探测 | `O(3 · len)` | `O(len)` | 单文件 |

其中快照合并是唯一的规模瓶颈：164 个 CSV 解析约 1.66 秒
（实测：扫描 0.59s + 解析合并 1.08s，5.3 ms/文件）。
当前的优化选择是**不优化** —— 看板是交互式生成而非实时刷新，
1.66 秒可接受，而引入 parquet 缓存会带来「缓存与原始数据不一致」的风险。
如果快照数量增长到千级，再考虑按需读取（只读筛选后的时间范围）。
